# raas-v2-sdk-node - Product Documentation

## General Overview

raas-v2-sdk-node is a **legacy, auto-generated Node.js client SDK** for the Tango Card RaaS (Rewards as a Service) v2 REST API. It was generated by APIMatic v2.0 for Tango Card, Inc. and is consumed by Plink's `main-api` backend as the `raas` npm package (installed directly from GitHub: `github:Fanbank/raas-v2-sdk-node#master`).

The SDK wraps the full RaaS v2 API surface: reward catalogs, brands, gift card orders, platform accounts, customer management, credit card funding, exchange rates, and system health. Tango Card is the gift card fulfillment provider behind Plink's reward issuance flow.

Because this is auto-generated code, it should be treated as **vendor code**. Manual edits are risky — changes to the upstream Tango Card API would normally be addressed by regenerating the SDK via APIMatic, not by hand-patching.

## System Processes

### 1. API Controllers

- **What it does:** Exposes the full RaaS v2 API surface as static methods on seven resource-specific ES6 classes. Each method constructs the HTTP request (URL, headers, Basic Auth credentials), sends it via the HTTP client, and deserializes the response into a typed model instance. Both callback and Promise interfaces are supported simultaneously.
- **Why it exists:** Provides the calling application with a clean, typed JavaScript interface to the Tango Card REST API without dealing with raw HTTP, URL encoding, or JSON deserialization manually.
- **How it is used:** The caller imports the SDK (`require('raas')`), sets credentials in `configuration.js`, then calls static methods directly (e.g., `OrdersController.createOrder(body, callback)`). In `main-api`, the datasource at `server/datasources/tango.js` calls these methods to issue gift card orders and query accounts.
- **Data it handles:**
  - Input: Typed request models (e.g., `CreateOrderRequestModel`) or primitive identifiers (strings, dates).
  - Output: Typed response models (e.g., `OrderModel`, `AccountModel`) or typed exceptions (`RaasClientException`, `RaasServerException`).

### 2. Request/Response Models

- **What it does:** Defines 28+ plain JavaScript classes representing every request body and response shape in the RaaS v2 API. Each model extends `BaseModel`, declares field mappings via `mappingInfo()` (including nested model types and datetime fields), and provides `toJSON()` for serialization back to plain objects.
- **Why it exists:** Enables strongly-typed, self-documenting data exchange with the RaaS API. `ObjectMapper` uses the `mappingInfo()` metadata to hydrate nested models (e.g., `OrderModel` contains `CurrencyBreakdownModel` for `amountCharged`, and `RewardModel` for `reward`).
- **How it is used:** Request models are instantiated by the caller and passed to controller methods. Response models are returned automatically by controllers after deserialization. Internally, `ModelFactory` creates instances by name string.
- **Data it handles:**
  - Request models: `CreateOrderRequestModel`, `CreateAccountRequestModel`, `CreateCustomerRequestModel`, `CreateCreditCardRequestModel`, `DepositRequestModel`, `UnregisterCreditCardRequestModel`.
  - Response models: `OrderModel`, `AccountModel`, `AccountSummaryModel`, `CustomerModel`, `CatalogModel`, `BrandModel`, `ItemModel`, `CreditCardModel`, `ExchangeRateResponseModel`, `DepositResponseModel`, `SystemStatusResponseModel`, and supporting value types.

### 3. HTTP Client & Configuration

- **What it does:** Provides the transport layer and SDK configuration. `RequestClient.js` converts an abstract request options object into an `npm request` call and wraps the response into `HttpResponse`/`HttpContext` objects. `configuration.js` holds `platformName`, `platformKey`, environment selection (`SANDBOX` or `PRODUCTION`), and base URL resolution. `APIHelper.js` provides URL template substitution, query parameter appending, JSON serialization, `null` cleaning, and datetime stringification. `LogConfig.js` configures `winston` to log to both console (info level) and a `logfile.log` file (debug level).
- **Why it exists:** Decouples the controllers from direct `request` library usage and centralizes all credential and environment management in one place.
- **How it is used:** `configuration.js` is modified by the caller to set credentials before making any API call. The default values in the repo (`platformName: 'QAPlatform2'`, `platformKey: 'apYPfT6H...'`) are sandbox test credentials — **these must be overridden in production**. `RequestClient` is called internally by every controller method and is not invoked directly by the application.
- **Data it handles:**
  - Input: Credential strings, environment enum, HTTP request options (URL, method, headers, body, auth).
  - Output: `HttpResponse` (statusCode, headers, body string), `HttpContext` (request + response pair), formatted URLs.

### 4. Exceptions & Object Mapping

- **What it does:** Defines a typed exception hierarchy for RaaS API errors and provides the deserialization engine. `APIException` is the base. `RaasClientException` covers 4xx errors (400, 403, 409) and includes an `errors` array of `RaasClientErrorModel`. `RaasServerException` covers 5xx errors (500, 503) and includes an `errors` array of `RaasServerErrorModel`. `RaasGenericException` covers 401, 404, and other unspecified error codes. `ObjectMapper` recursively maps raw JSON objects to typed model/exception instances using field metadata from `mappingInfo()`. `ModelFactory` resolves model class names to constructor instances.
- **Why it exists:** Allows the calling application to distinguish between client-side errors (invalid request data, auth failures) and server-side errors (Tango Card infrastructure issues) and handle them differently.
- **How it is used:** `BaseController.validateResponse()` is called automatically on any non-2xx response. The returned exception object is passed to the callback as the first argument and used to reject the Promise. The caller checks the error type to decide on retry logic or error messaging.
- **Data it handles:**
  - Input: HTTP status codes, raw JSON error response bodies.
  - Output: Typed exception instances with `reason`, `context`, `timestamp`, `requestId`, `path`, `httpCode`, `httpPhrase`, and `errors` fields.

## General System Flow

```
main-api (server/datasources/tango.js)
    |
    | require('raas') + set configuration.platformName / platformKey
    v
Controller.method(params, callback)
    |
    | APIHelper builds URL, validates required params
    v
RequestClient sends HTTP request (Basic Auth)
    |
    +-- 2xx response
    |       |
    |       v
    |   ObjectMapper.mapObject(JSON, 'ModelName')
    |       -> nested model fields hydrated recursively
    |       -> datetime fields parsed via moment
    |   callback(null, typedModel, context)
    |   Promise.resolve(typedModel)
    |
    +-- non-2xx response
            |
            v
        BaseController.validateResponse(context, endpointName)
            -> maps status code to exception type
            -> ObjectMapper.mapObject(errorJSON, 'ExceptionClass')
        callback(errorObj, null, context)
        Promise.reject(errorObj)
```

**Typical order placement flow (from main-api perspective):**
1. `main-api` configures `raas.configuration.platformName` and `platformKey` from environment variables.
2. Calls `OrdersController.createOrder(body)` where `body` is a `CreateOrderRequestModel` with `accountIdentifier`, `amount`, `utid`, `customerIdentifier`, `sendEmail`.
3. SDK POSTs to `/orders` with Basic Auth.
4. On 201 response: returns `OrderModel` containing `referenceOrderID`, `status`, `reward` (with `RewardModel` containing credential links), `amountCharged` (with `CurrencyBreakdownModel`).
5. On 4xx/5xx: returns `RaasClientException` or `RaasServerException` with structured error details.

## External Dependencies

| Service | Purpose | Criticality |
|---------|---------|-------------|
| **Tango Card RaaS API (SANDBOX)** | Integration testing endpoint (`integration-api.tangocard.com/raas/v2`) | Required for running the test suite |
| **Tango Card RaaS API (PRODUCTION)** | Live gift card issuance (`api.tangocard.com/raas/v2`) | Critical — without it, Plink cannot issue rewards |
| **npm: request** | HTTP transport (v2.x) | Critical — all API calls depend on it |
| **npm: winston** | Logging (v2.x) | Low — only affects observability |
| **npm: moment** | RFC3339 datetime parsing/formatting | Medium — datetime fields in orders and accounts |

## Metrics and Impact

- **7 controller classes** covering the complete RaaS v2 API surface: Accounts, Catalog, Customers, ExchangeRates, Fund, Orders, Status.
- **28+ model classes** covering all request/response shapes including nested value types.
- **Dual interface**: every controller method supports both Node.js callback style and Promise style simultaneously.
- **Two environments**: SANDBOX (test credentials, fake money) and PRODUCTION (real credentials, real money). The default configuration in the repo is SANDBOX — this is intentional for safety.
- **Consumed by main-api** as `"raas": "github:Fanbank/raas-v2-sdk-node#master"` via `server/datasources/tango.js`. This is the only known Plink consumer of this SDK.
- **Legacy status**: No active development. Treat as read-only vendor code unless a Tango Card API change forces a patch or full regeneration via APIMatic.
- **Test suite**: Integration tests in `test/Controllers/` hit the real SANDBOX API using hardcoded test identifiers (`sdkautotest1`, `sdkautotest2`, etc.). Tests are not mocked and require a live Tango Card sandbox connection.
